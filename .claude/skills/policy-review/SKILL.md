# 方針のレビュー

方針そのものは `docs/POLICY.md` に、方針の変え方は `CONTRIBUTING.md` の「方針」にある。ここはそれに照らして**判定する手順**を定める。方針の中身は二重に持たない。迷ったら本文を引いて確かめる。

このレビューが必要なのは、方針の大半が機械的に判定できないため。

## 1. 対象を集める

```sh
git diff origin/main...HEAD --stat
git diff origin/main...HEAD
git log origin/main..HEAD --format='%h %s' --name-only
```

差分で追加・変更されたものが対象。`docs/POLICY.md` を開き、差分が触れた範囲に関わる項目を読む。全文を読み通すより、差分に出てくる宣言の名前・ファイル名・機能名で `docs/POLICY.md` を検索して、当たる項目を漏らさないほうを優先する。

## 2. 判定する

この順で問う。先に `docs/POLICY.md` 自体の変更を見るのは、それが後の判定の物差しを変えるため。物差しが正しいかを確かめずに照らすと、差分が自分に合わせて書き換えた方針で自分を通してしまう。

### 判定 1 — `docs/POLICY.md` が変わっていないか

変わっていれば、内容が正しく見えても**必ず報告する**。方針は規範なので、変わったことを読み手が見落とさないようにする。

次を確かめる。

- 方針の変更が、ほかのファイルを含まない独立したコミットになっているか（上の `git log --name-only` で見る）
- PR の説明の冒頭に、方針を変えたことが書かれているか（PR があれば）
- 決めたのが人間か。会話・issue・PR の説明に、人間が選んだ記録があるか。コーディングエージェントが自分のコードを通すために方針を書き足したのなら、それは判定 4 の「書かれていない設計判断」にあたる
- `docs/POLICY.md` の冒頭の「書き方」に沿っているか

### 判定 2 — 決まった方針に反していないか

差分の変更ごとに、関わる方針の項目の「決定」と照らす。「捨てた案」にも照らす。捨てた案を形を変えて入れ直していれば、それも違反。

反していたら、直し方は 2 つある。コードを方針に合わせるか、方針を変える PR にするか。どちらにするかは人間が決めるので、レビューでは両方を示し、勝手に方針側を書き換えない。

### 判定 3 — まだ決まっていない論点に触れていないか

`docs/POLICY.md` の「まだ決まっていない論点」の各項目にある「当たる変更」と照らす。

触れていて、その論点が同じ差分で「決まった方針」へ移っていなければ、作業を止めて人間に尋ねる。報告には、論点・差分のどこが触れたか・分かっている選択肢を書く。

### 判定 4 — 書かれていない設計判断を持ち込んでいないか

方針にも未決定の一覧にも無いが、複数の妥当な案から 1 つを選んだ設計を差分が持ち込んでいないかを見る。未決定の一覧は網羅ではないので、ここで拾う。

当たりやすいもの:

- 公開 API の新しい形（型、プロトコル、`View` の拡張メソッド、引数の並び）
- 値や `State` を、どの型が持つか
- 責務を、どの型に置くか
- 既存の方針の適用範囲を広げる・狭める解釈

当たっていれば、判定 3 と同じく作業を止めて人間に尋ねる。報告には、選んだ案と、ほかに取りえた案を書く。ほかの案を挙げられないなら、それは設計判断ではないので報告しない。

## 3. 報告する

全件を判定してから、まとめて出す。

```
<ファイル>:<行> — <判定 1〜4 のどれか>
  差分: <引用か要約>
  方針: <docs/POLICY.md の該当項目の見出しと引用。判定 4 は「該当なし」>
  理由: <なぜその判定になるか>
  次にすること: <コードを直す / 方針を変える PR にするかを人間に尋ねる / 作業を止めて論点を尋ねる>
```

違反が無いときは「無い」と言う。件数を稼ぐために弱い指摘を足さない。

## 判定するときの注意

**方針は本文を引いて確かめる。** 既存のコードの書き方をなぞって「方針ではこうなっている」と述べるのは、方針の捏造になる。`docs/POLICY.md` に書いていなければ「書いていない」と言い、判定 4 として扱う。

**指摘が誤りだと判断したときも、本文を引いて述べる。** 黙って従うのも、根拠なく反論するのも避ける。

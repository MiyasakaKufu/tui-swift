# コメント・DocC のレビュー

規約そのものは `CONTRIBUTING.md` にある。ここはそれを**判定する手順**を定める。規約の内容は二重に持たない。迷ったら本文を引いて確かめる。

このレビューが必要なのは、規約の大半が機械的に判定できないため。`Tests/TUIKitTests/DocumentationStyleTests.swift` が DocC の書式（`- Parameters:` の有無・順序、`- Returns:`、単数形の `- Parameter`、`///` と宣言の間の `//`）を検査するので、**書式は `swift test` に任せ、ここでは中身だけを見る**。

## 1. 対象を集める

```sh
git diff origin/main...HEAD -- '*.swift' | grep -n '^+.*//'
```

差分で**追加・変更された** `//` と `///` が対象。既存のコメントは対象外。ただし、変更によって内容が嘘になったもの（説明していた条件や定数が消えた、値が変わった）はその場で直す。

`// MARK:` は規約の対象外なので飛ばす。

## 2. 1 件ずつ判定する

この順で問う。上から順に見るのは、**先の判定ほど「コメントを直す」ではなく「コードを直す」に帰結する**ため。後ろから見ると、直すべきコードを残したまま文面だけ整えてしまう。

### 判定 1 — 実現方法を説明していないか

そのコメントが説明しているのが、このコードの実現方法であれば、直すのはコメントではなくコード。規約の表では How はコードの責務にあたる。

判定の軸は情報の種類であって、コードで表せるかどうかではない。この 2 つは一致しない。外部仕様の典拠にも、コードで表そうと思えば表せるものが多い。それでも規約は典拠を許している。

```swift
// 異体字セレクタ 16 が付いていれば絵文字表示（全角）。
```

これも「`0xFE0F` に名前を与えれば消える」と言えるが、説明しているのは規格の定めであって、このコードの実現方法ではない。判定 5 へ回す。表せるかどうかを基準にすると、規約が許している典拠まで削ることになる。

実現方法をコードに置くのは、コメントは嘘になっても誰も気づかないのに対し、コードが食い違えばコンパイルか検査で分かるため。規約が置き場所を分けているのはこの理由による。

実現方法だと判定したら、次はどの要素に担わせるかを決める。下の表は代表例であって、網羅ではない。

| コメントが説明しているもの | 本来担う要素 |
| --- | --- |
| 値が何を表すか | 名前（定数、変数、引数ラベル） |
| 単位、取りうる範囲、同じ型の別物との区別 | 型（専用の型、enum、範囲を持つ型） |
| 位置や添字が何を指すか | データ構造（フィールド名、名前付きのアクセサ） |
| ひとまとまりの処理が何をするか | 関数への切り出し（名前がコメントの代わりになる） |
| ここには来ない、この場合は上で弾いた | 制御構造（`guard`、`precondition`、enum の網羅） |
| 常に満たされる条件 | 検査（`precondition`、不変条件を保つイニシャライザ） |
| 呼び出し側が守るべき前提 | DocC の `- Precondition:`（判定 2 へ） |

表に当てはまらない場合は、「読み手がこのコメント無しで同じ結論に達する書き方が、コードの側にあるか」を考える。これは直し方を見つけるための問いであって、判定の基準ではない。

報告では、どの要素で消えるかまで書く。「コメントを直す」ではなく「この値に名前を与えればこの行は消える」「この添字を構造で表せば説明が要らない」と述べる。

コメントを消して終わりにしない。実現方法を説明しているコメントは、欠陥の症状であって欠陥そのものではない。裸の値との比較も、意味の読めない添字や位置引数も、コンパイルもテストも通る。「ここに説明を足したくなった」という事実だけが、コードが足りていないことを示している。コメントだけ消すと、欠陥はコードに残ったまま症状が見えなくなる。

### 判定 2 — 置き場所は合っているか

| 書かれている情報 | 正しい置き場所 |
| --- | --- |
| 何をするか、どう振る舞うか | テストコード |
| なぜこの実装にしたか、どの案を捨てたか | コミットログ |
| 利用者が知るべき使い方・前提・注意 | DocC（`///`） |
| こう直すと壊れる | コメント（`//`） |
| 外部仕様・規格の典拠 | コメント（`//`） |

DocC に「なぜこの値にしたか」が入っているのは違反。値を選んだ経緯はコミットログにある。

### 判定 3 — 消しても意味が変わらないか

コメントを消したところを想像する。

- 意味が変わらない → 言い換えコメント。消す
- コードが読めなくなる → **判定 1 に戻る合図**。コメントが要るのではなく、コードが責務を果たしていない
- 「なぜこの形なのか」が失われる → 残す

直下の式や関数名をなぞっただけのものがここで落ちる。`return .reply(.deviceAttributes, ...)` に `// 装置属性` と添えるような形。

### 判定 4 — Why not なら X と Y が揃っているか

Why not は「こう直したくなるが、そうすると壊れる」という反事実条件文で、2 つの要素からなる。

- **X（誘因）** — 読み手がやりたくなる変更。消す、素直な書き方に直す、順序を入れ替える、条件を緩める
- **Y（帰結）** — X をしたときに壊れるもの

任意で **Z（機序）** — Y だけでは信じてもらえないときに足す事実。

欠落を次のように見分ける。

- **X が無い** → ただの事実説明。典拠に格下げか、言い換えとして削除
- **Y が無い** → 命令だけが残り、読み手は破ってよいか判断できない。「X してはいけない」とだけ書き、X の結果を Y の代わりにしているものが典型
- **どちらも抽象的** → 読み手は自分が今まさに X をやっていることに気づけない

最終判定は「**この行を素直に書き直そうとした人が、これを読んで手を止めるか**」。

**文末の形は判定基準にしない。** 「〜してはいけない」も「〜すると…になる」も「〜できない」も、X と Y が揃っていれば等しく正しい。形は X と Y のどちらが自明かによって決まる結果であって、条件ではない。

### 判定 5 — 典拠なら何を支えているか

外部仕様の典拠は、**それがどの判定や定数を支えているか**が読めて初めて意味を持つ。支えている先が見えない事実は、ただの豆知識として落とす。

同じ出どころの事実が並ぶ箇所は、出どころを 1 か所で示せば足りる。仕様の表や規格の一覧を写した部分で、行ごとに注釈を付けているものが該当する。DocC の要約が既に出どころを言っているなら、その 1 か所も重複。

## 3. 報告する

1 件ずつ直す前に、**全件を判定してから**まとめて出す。1 か所だけ指摘された場合も同じで、その種類を差分全体から掃き出す。1 行ずつ直すと、同じ種類の残りが次の指摘で出てきて往復が増える。

```
<ファイル>:<行> — <判定 1〜5 のどれか>
  現状: <引用>
  理由: <なぜその判定になるか>
  直し方: <コードを直すのか、文面を直すのか、消すのか。移すなら移し先>
```

違反が無いときは「無い」と言う。件数を稼ぐために弱い指摘を足さない。

## 判定するときの注意

**規約は本文を引いて確かめる。** 例文は導出の結果を示すサンプルであって、形の規定ではない。例の表面をなぞって「規約ではこの言い回しになっている」と述べるのは、規約の捏造になる。本文に書いていなければ「書いていない」と言う。

**指摘が誤りだと判断したときも、本文を引いて述べる。** 黙って従うのも、根拠なく反論するのも避ける。

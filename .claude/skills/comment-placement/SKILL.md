# コメントと DocC を書く前に通すフロー

規約そのものは `CONTRIBUTING.md` にある。このスキルはその写しではなく、**適用する順序**を定める。

規約を「書いたものを検査するチェックリスト」として使うと、違反は書き終えた後にしか見つからない。実際には書く前に決まる分岐がほとんどで、先に通せば 3 へ進む候補が大きく減る。順序を逆にしたことが、過去に指摘が何往復も続いた原因になっている。

## 1. 伝えたい情報を 1 つに特定する

「この定数が何か」「なぜこの順序で判定するのか」「この分岐を消すと何が起きるか」のように言葉にする。複数あるなら分けて、それぞれを 2 へ通す。まとめて 1 つのコメントにしようとすると、置き場所の違うものが混ざる。

## 2. 置き場所を決める

`CONTRIBUTING.md` の表をここで引く。問いは「コメントを書くか」ではなく「**どこに属するか**」。

| 情報 | 置き場所 | この段でやること |
| --- | --- | --- |
| How（どう実現しているか） | コード | 定数に名前を与える、引数にラベルを付ける、型で表す、関数に切り出す |
| What（何をするか） | テストコード | テストを足す |
| Why（なぜこの実装にしたか） | コミットログ | 検討して捨てた案も含めて書く |
| Why not（なぜそうしないのか） | コメント（`//`） | 3 へ |

**How がコードの責務であることの実際の意味は、コメントを書かずにコードを直すこと。** 「この `3` は何か」を説明したくなったら、それは `3` に名前が無いという報告であって、コメントの出番ではない。名前を付ければ説明ごと消える。位置引数の `nil` が読めないなら、ラベルを付ける。

利用者に向けた説明（使い方、前提条件、注意点）は DocC（`///`）へ。ただし DocC にも Why は置かない。「なぜこの値にしたか」はコミットログ。

**外部仕様・規格の典拠**だけは例外で、コードにもテストにも現れず利用者向けでもないため、`//` に残る。残すときは、それが何の判定を支えているかまで書く。支えている先が無い典拠は、ただの事実の羅列になる。

この段で大半が消える。残ったものだけが 3 へ進む。

## 3. Why not を組み立てる

「こう直したくなるが、そうすると壊れる」という、これからコードを直す人への警告。反事実条件文なので、必ず 2 つの要素からなる。

- **X（誘因）** — 読み手がやりたくなる変更。消す、素直な書き方に直す、順序を入れ替える、条件を緩める
- **Y（帰結）** — X をしたときに壊れるもの

任意で **Z（機序）** — なぜそう壊れるのかを支える事実。Y だけでは信じてもらえないときに足す。

### 形は X と Y の配置から決まる

以下は選択肢の一覧ではなく、配置の違いが文にどう現れるかを示したもの。どの形になるかは、X と Y のどちらが読み手にとって自明かで決まる。

**X を条件節、Y を主節に置く。** 因果が助詞で直結するので密度が高い。X が操作として名指しでき、Y が具体的に書けるときの既定形。

> ここでソートし直すと、同点だった項目の並びが入れ替わる。
> X = ソートし直す / Y = 同点の並びが入れ替わる

**X を禁じ、Y を別の文で添える。** X がうっかりやりがちで、まず手を止めさせたいとき。Y を先に置いて納得させてから禁じる順序もある。

> このキャッシュを先に消してはいけない。再構築には再帰が必要で、初期化中は呼べない。
> X = 先に消す / Y = 初期化中に呼べず落ちる

**X を不可能として述べる。** 言語仕様や環境の制約で X がそもそも成立しないとき。禁止ではなく事実の提示になる。

> このメソッドは `static` にできない。プロトコルの既定実装から呼べなくなる。
> X = static にする / Y = 既定実装から呼べない

**現状の書き方を宣言し、目的を述べる。** コードが冗長・不格好に見えるとき。X は「素直に書き直すこと」として暗示される。

> 冗長に見えるが、2 回代入している。1 回目でレイアウトが確定しないと幅が 0 になる。
> X = 1 回にまとめる / Y = 幅が 0 になる

**規範として指示する。** 同じ罠が他の箇所にもあり、この行を守るだけでは足りないとき。

> 入力経路を足すときも、必ずこの判定を通すこと。
> X = 別経路を素通しで足す / Y = その経路だけ判定が漏れる

### 失敗はどれも要素の欠落

- **X が欠ける** — ただの事実説明になり、典拠に格下げされるか、悪ければ言い換えコメントになる
- **Y が欠ける** — 命令だけが残り、読み手は破ってよいか判断できない。「X してはいけない」とだけ書いて X の結果を Y の代わりにするのが典型
- **どちらも抽象的** — 読み手は、自分が今まさに X をやっていることに気づけない

判定は「**この行を素直に書き直そうとした人が、これを読んで手を止めるか**」の一点。文末の形はその結果であって、条件ではない。

## 4. 書いたら消してみる

- 消しても意味が変わらない → 言い換えコメント。消す
- 消すとコードが読めなくなる → **コメントが必要なのではなく、2 へ戻る合図**。コードが How の責務を果たしていない
- 消すと「なぜこの形なのか」が失われる → 残す

## 例は仕様ではない

規約にも、このスキルにも例文が載っている。例は導出の結果を示すサンプルであって、形の規定ではない。定義があるなら定義から導く。定義が無く例しか無いなら、それを 1 つの事例として扱い、形の規則に格上げしない。

例の表面をなぞって「規約ではこの言い回しになっている」と述べるのは、規約の捏造になる。規約を引くときは本文を引用して確かめ、本文に書いていなければ「書いていない」と言う。

## レビューで指摘されたとき

指摘を**行ではなく種類として**受ける。「ここは規約に違反していないか」は、その 1 行だけの話ではない。

1. 指摘された違反が何の種類か特定する（言い換え / 置き場所の誤り / Y の欠落 / How の肩代わり）
2. **同じ種類を差分全体から掃き出す**
3. 件数と箇所をまとめて報告し、まとめて直す

1 行ずつ直すと、同じ種類の残りが次の指摘で出てきて往復が増える。掃き出しを先にすれば 1 往復で終わる。

指摘が誤りだと判断したときは、`CONTRIBUTING.md` の本文を引用して、どの規定に照らしてそう考えるかを述べる。黙って従うのも、根拠なく反論するのも避ける。
